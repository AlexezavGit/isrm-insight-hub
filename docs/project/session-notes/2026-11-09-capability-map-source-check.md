### MemberPress

Алекс повідомив, що його оцінка ймовірності MemberPress як CRM ISRM становить **97%**, і що інших CRM tools він не знає. Це пряме знання/оцінка замовника, не незалежне підтвердження й не статистична ймовірність. Рішення робочого плану: MemberPress — перша обов’язкова цільова CRM-інтеграція; відповідний числовий паспорт додано в `REGISTRY.csv` зі статусом `assumption`.

Офіційні джерела MemberPress документують Developer Tools REST API actions та webhooks; add-on залежить від плану/налаштування, а доступ до endpoint-ів не підтверджений для ISRM. Далі перевірити з адміністратором інсталяцію/план, дозволені поля й actions, webhook events, sandbox, scopes та read/write напрямки. Не ставити питання, яку CRM обрати; це питання вже вирішено на рівні цільового адаптера. Технічна готовність і data contract лишаються відкритими.

Вибірка репрезентативна, а не повний ринковий census чи feature-by-feature аудит кожного продукту з початкового переліку. Вона коригує надмірно широкі твердження про відсутність у конкурентів інтеграцій, introduction paths, compliance або проектного відбору. Водночас вона не доводить, що окремий постачальник поєднує всі функції Hub, і не доводить, що такого постачальника немає. Категоричну унікальність не виносити в клієнтську презентацію без подальшого систематичного порівняння.

### Рекомендована межа та план

Мапа рекомендує доменне ядро `01–08, 22`, інтеграційну платформну основу `23`, MemberPress як перший адаптер, модулі `09–10, 15–21` та умовний manifest `24`. Критичні горизонтальні вимоги: identity resolution, provenance, доступ/data governance. Єдиний numeric trust-score не є підтвердженим baseline; пояснювані стани доказів кращі за непрозорий агрегат. Це рекомендація для погодження з Алексом, не вже схвалена схема бази даних.

План зберігає branch/worktree cleanup як перший операційний пріоритет, але дозволяє desk research/documentation йти паралельно. UI-огляд і кодові зміни заблоковані до підтвердження актуального worktree та збереження його незакомічених змін. Видалення, кодові зміни, commit, push та deployment не виконувались.

Попередній широкий пошук не дає підстави для висновку «жоден конкурент не поєднує функції» або узагальнення доступності API для GLG, AlphaSights, Guidepoint, Third Bridge, Catalant, Expertise Finder, CRM асоціацій чи relationship-intelligence продуктів. Ці твердження у двох чернетках позначені як такі, що потребують поелементної перевірки. Ціни й комерційні умови не досліджувались.

## Основні аналітичні поправки

- Членство/renewal, навчання, публікації й події не можна прив’язати до конкретного ISRM постачальника без відповіді власника системи.
- Доступність vendor API не є дозволом на дані конкретного клієнта або доказом потрібного endpoint/плану.
- «Довіра» не дорівнює єдиному score. Потрібні типізовані докази, походження, дата, обмеження, статус рецензування та доступ; агрегування лишається відкритим рішенням.
- Згода не є універсальною правовою підставою для кожного потоку; потрібна карта мета/підстава/роль/права та юридична перевірка.
- Реєстрація на подію, присутність, сертифікат, публікація й відгук мають різну семантику; автоматично перетворювати їх на доказ компетентності не слід.
- Залежності конфігуратора треба розділяти на обов’язкові передумови, рекомендовані джерела, передавання/результати й правила доступу.
- Залучення, накопичення експертизи, клієнтський intake/referrals і Situational Awareness залишені окремими кандидатними напрямками, а не зведені до одного затвердженого кільця.

## Незакриті питання / наступна дія

1. Виконати перший пріоритет чинного плану: повну інвентаризацію refs/worktree та показати точні локальні кандидати на прибирання для підтвердження.
2. Після цього перевірити саме актуальний кодовий worktree на desktop і mobile; тільки тоді оцінювати реалізацію/зрілість можливостей.
3. Продовжити дослідження кандидатів-постачальників за офіційними першоджерелами, фіксуючи точну функцію, URL, дату й обмеження кожного джерела.
4. Показати мапу й альтернативи для погодження до концептуальних змін конфігуратора.
5. Отримати від ISRM фактичні системи-власники, права/API/експорт, власників процесів та вимоги до даних.

Жодне рішення щодо межі ядра, trust-score, обов’язкового consent gate, преміальних сервісів, SaaS, бюджету чи унікальності продукту не ухвалено.
